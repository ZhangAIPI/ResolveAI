# 当前问题：模型不会搜证，还是题目与工具不好用？

我们的目标是判断开源模型能否主动获得足以验证物品声明的证据。每个失败应能定位到题目、看图、动作选择、工具参数或取证后的整合，而不是只给一个总分。

用同一题做四种条件：

1. 只给初始图片，直接判断。
2. 环境按固定请求补齐原图，再让模型直接判断。
3. 模型自己选操作菜单，自己决定检查、裁剪、放大、比对、请求或停止。
4. 模型自己填写完整工具调用与引用参数。

另外分别在菜单和完整接口下让关键原图无法提供，观察模型如何处理失败；不自动假定它一定应该弃答。

正式能力评测的入库门槛：题干能明确指向目标；工具能按约定返回材料；人看完整材料能可靠判断。来源标签与像素是否足以判断必须分开，外观相似不自动证明同一实物。尚未通过这些门槛的题只用于开发诊断。

先确认固定请求能拿到正确照片、底层物品状态不变。随后找出“初始答错、补齐后答对”的题。这些题才有机会检验搜证是否有用：

| 观察到什么 | 下一步 |
|---|---|
| 菜单成功，完整接口失败 | 先修工具接口、参数与引用 |
| 补齐后能答对，菜单下仍不取证 | 仍答错时，复核后作为搜索策略训练候选失败 |
| 取到原图仍答错 | 检查多轮历史与证据整合 |
| 补齐后仍答错 | 先复核题目和图片，再判断感知能力 |
| 初始图片已经答对 | 不能用来证明索证收益 |

诊断版本使用 60 个 MVTec 状态题与 60 个 CO3D 身份题，支持/反驳各半。身份题公开目标区域，排除“物体究竟指哪个”的歧义；负例先用不同类别物品的容易控制题，不声称完成细粒度身份负例建设。原始图片保持不变，三模型与全部条件固定后运行。

菜单是诊断支架：模型选择一个明确列出的实际调用，系统负责把这个选择送给工具。菜单的有限选项由可见图片、公开请求选项和预算生成，不读取身份答案。它不测试自由坐标、参数生成或完整证据链。完整接口单列这些能力；两者共享基础工具种类、预算 12 和六回合上限。

这批题用于开发诊断。来源标签还不是独立审核过的充分性标签；构造身份负例可能复用原始序列，因此不将生成题视为独立实物，也不报告独立案件置信区间。模型选择任何确定答案，都不会因为原图缺失被机械判成无依据。

运行入口：[run_capability_diagnostic.py](../scripts/run_capability_diagnostic.py)。模型、数据与原生轨迹保存在 GPU 节点 p62；仓库只保存代码和精简报告。只有所有条件完成且请求自检通过，才生成完整报告。

这一步先判断应修 benchmark 的哪一部分、哪些失败值得未来训练。它不替代 proposal 中困难身份匹配、状态变化、证据链、动作分叉和训练对照的完整 benchmark。

## 一道实际失败题（完整诊断仍在运行）

题目：“照片中的瓶子有可见缺陷。”图片来自 MVTec，来源标注为瓶口小破损（broken_small）。案件 `mvtec-6621d76a324f6e05d5838d62`，模型 Qwen3-VL-8B。

- 只给模糊预览：回答“需要更多证据”。
- 系统请求并提供原图：回答“支持”，与来源标注一致。
- 模型自己选操作：inspect → zoom → crop → finish；始终操作预览，没有请求原图，最终回答“反驳”。这些调用全部合法，没有格式错误。

这里已排除“工具拿不到原图”和“该模型完全看不懂这张原图”。它是一条过早停止、未获取有用材料的候选失败；还需复核题目与证据，不能由一个案例概括所有模型。原图缺失本身也不是错误，若其他可见材料已经足够，模型可直接判断。

开发模型代码固定为 `f304912`。本页示例来自实际记录，未改写模型的动作或结论；原生轨迹保存在 GPU 节点 p62。完整三模型结果只有全部条件完成后才发布。
